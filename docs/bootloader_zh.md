BootLoader 升级插件（Ymodem 上位机）
=======

给 COMTool 增加一个内置插件，用于配合 **APM32E103 BootLoader** 通过串口升级 APP 固件。
上位机扮演标准 **Ymodem（CRC-16 模式）发送方**，与设备端 `tools/host_updater.py` 协议完全一致，
但额外做了「设备日志与本机日志分离」「升级结果端到端校验」「全流程可视化」三件事。

> 设备端工程：`F:/Code/TH/Bms_FBL`（本文档中所有协议常量均以该仓库源码为准）
> 相关源码：`COMTool/plugins/bootloader.py`、`COMTool/plugins/bootloader_ymodem.py`


## 一、设备端协议规格（权威）

### 1.1 Flash 分区（`Bootloader/Include/boot_config.h`）

| 分区 | 地址 | 大小 | 说明 |
|------|----------|--------|------|
| BootLoader | `0x08000000` | 8KB | 固定启动区 |
| 标志位区 | `0x08002000` | 4KB | 双 bank 环形日志 + 磨损均衡 |
| 运行 APP 区 | `0x08003000` | 100KB | 上电实际运行的 APP |
| 备份 APP 区 | `0x0801C000` | 100KB | 升级时先写入这里 |
| 保留 | `0x08035000` | 44KB | 预留 |

- `APP_MAX_SIZE = 0x19000 = 102400`（单份 APP 最大长度）
- `BL_BAUDRATE = 115200`（8N1），`BL_WAIT_MS = 3000`（运行区有效时的邀请窗口）
- `BL_RX_TIMEOUT_MS = 500`（设备收包/收字节超时），`YMODEM_INVITE_MAX = 600`

> 注：APP 的链接起始地址必须是 `APP_RUN_BASE = 0x08003000`。可用复位向量自检：
> 裸 bin 偏移 4 处的 4 字节应为 `0x08003xxx`。

### 1.2 固件头（强制，32 字节）

升级文件最前面必须是 32 字节固件头，**由上位机生成**（`boot_protocol.h: fw_header_t`）：

| 偏移 | 字段 | 值 |
|------|------|----|
| 0 | `magic` | `0x424D5331`（"BMS1"） |
| 4 | `fw_type` | `1`（APP） |
| 8 | `hw_id` | `1`（硬件型号） |
| 12 | `version` | 固件版本，**权威版本，防降级依据** |
| 16 | `size` | 固件数据长度（**不含头**） |
| 20 | `header_crc` | 前 20 字节的 CRC32（zlib/PKZIP） |
| 24 | `reserved[0]` | 0 |
| 28 | `reserved[1]` | 0 |

设备端逐项校验（`boot_protocol.c: fw_header_check()`）：magic / fw_type / hw_id /
`0 < size ≤ APP_MAX_SIZE` / `size + 32 == file_size` / `header_crc` / `version ≥ min_version`。
任一不符 → 设备发**双 CAN** 并返回 `YMO_ERR_HDR`。

**关键约定：**

- 文件名包里报给设备的 `file_size` = **32 + 裸 bin 大小**（含头），合法范围 `32 < file_size ≤ 102432`
- 设备累计的 CRC32 **只覆盖固件数据、不含固件头** → 主机可直接用 `zlib.crc32(裸bin)` 对拍
- **防降级**：若设备里已有有效 APP（版本 V），则 `min_version = V`，新固件 `version < V` 直接被拒
- `;V=0xXXXX` 文件名后缀会被解析，但最终以固件头里的 `version` 为准

### 1.3 升级时序（`boot_main.c` / `boot_protocol.c`）

```
[上电/复位] 设备打印 "BootLoader V1.1" + banner 文本
      ↓
设备发 'C' 邀请（强制升级模式持续发；运行区有效时只在 3s 窗口内发）
      ↓
主机发 文件名包 SOH seq=0 : "<name>\0<file_size>\0" 补 0 到 128B
      ↓
设备：解析 → 立即 ACK → 擦除备份区(50 页，秒级) → 擦除完再发 'C'
      ↓
循环（每包 1024B，末包 0x1A 填充）
   主机发 STX seq=N  →  设备 drain 环 → delay 100ms → 收包 → 写 Flash → ACK
   校验失败回 NAK，主机重传同一包（最多 5 次）
      ↓
EOT → ACK+'C' → EOT → ACK+'C' → 空包(SOH seq=0 全 0) → ACK
      ↓
设备打印 "YMODEM: 接收完成 size=<n> crc=0x<8hex>"
   → 拷贝备份区→运行区 → 校验 → 写标志位
   → "UPDATE OK, jump to APP..."  或  "UPDATE: xxx失败"
```

**取消**：主机发双 `CAN`(0x18)。

### 1.4 设备端实现带来的硬约束

| # | 约束 | 依据 |
|---|------|------|
| C1 | 文件名包是**先 ACK 后擦除**，擦除期间主机**绝不能发数据**（擦除脉冲会 stall CPU 导致丢字节） | `boot_protocol.c` |
| C2 | 强制升级模式下设备每 ~100ms 发一个 `'C'`，残留的 `'C'` 会排在 ACK 之前 → 主机等 ACK 时必须**忽略 'C'**，收到邀请后要**清空输入缓冲** | `host_updater.py: wait_name_ack()` |
| C3 | 每包前设备先 `drain 环` 再 `delay 100ms`，注释明确"验证主机 byte_gap ∈ {0,0.1,0.5,1,2}ms 均稳" → **主机整包连发是安全的** | `boot_protocol.c` |
| C4 | 每包设备侧开销 ≥100ms + Flash 写入 → 100KB 约需 20~25 秒，主机发送速率不是瓶颈 | 同上 |
| C5 | UART 接收环 1040 字节，刚好能缓存一个 1029 字节包 | `hal_uart_apm32.c` |
| C6 | 设备启动/升级日志是 **UTF-8 文本，与协议字节混在同一条流里** | `boot_main.c` |


## 二、COMTool 侧架构

### 2.1 分层

```
COMTool 主窗口 (MainWindow)
   └─ PluginItem            ← 每个 Tab 一份，自动注入左侧连接面板
        └─ bootloader.Plugin (Qt 插件：UI + 生命周期 + 串口适配器)
             ├─ _PortAdapter        ← 把「异步收发」适配成「同步阻塞串口」
             └─ bootloader_ymodem.YmodemLink
                  ├─ 文本/协议解复用（解决 C6）
                  ├─ 等待原语 wait_invite / wait_proto / read_line
                  └─ ymodem_send()   ← 协议状态机（握手/重传/双 EOT/结果解析）
```

### 2.2 文件清单

| 文件 | 职责 |
|------|------|
| `COMTool/plugins/bootloader_ymodem.py` | 协议核心：固件头构造、CRC16/XMODEM、组包、文本/协议解复用、发送状态机、结果解析、**离线自测（MockPort 设备模拟器）** |
| `COMTool/plugins/bootloader.py` | Qt 插件：`_PortAdapter`、三栏 UI、日志、参数校验、结果对拍 |
| `COMTool/plugins/__init__.py` | 注册 `bootloader.Plugin` |
| `COMTool/locales/*` | 新增文案的翻译（zh_CN 已 100% 覆盖） |

**未改动 COMTool 核心代码**，完全通过 `Plugin_Base` 既有契约接入。

### 2.3 异步接口 → 同步协议 的适配

Ymodem 是严格的「发一包 → 等 ACK」锁步协议，而 COMTool 插件接口是全异步的，这是本插件最核心的适配点：

| Ymodem 需要 | COMTool 提供 | 适配方式 |
|-------------|--------------|----------|
| `ser.write(bytes)` | `self.send(data, callback)` 入队后由独立线程发送 | 适配器 `write()` 等回调确认（**3s 超时**，断线不死等）；未连接立即报错 |
| `ser.flush()` | 无 | no-op（靠等 ACK 建立同步点） |
| `ser.read(1)` 阻塞 | `onReceived()` 在**串口接收线程**回调 | 适配器维护 `queue.Queue` + 字节缓冲，语义对齐 pyserial（凑够 n 字节或超时） |
| `ser.timeout` | 无 | 适配器自身属性 |
| `ser.reset_input_buffer()` | 无 | 清空队列（丢弃残留的 `'C'`） |
| 逐字节 `byte_gap` | **架构上不可行**（每字节一次队列往返） | 默认整包连发；低速模式改用「分块 + 块间隔」近似 |

### 2.4 关键设计决策

| 决策 | 原因 |
|------|------|
| **文本/协议解复用**放在 `YmodemLink` | 设备会把 `RECOVER OK` / `BACKUP invalid` 等文本与协议字节混发；而 `host_updater.wait_for_C()` 只读 1 字节且要求 `== 'C'`，遇到 banner 文本就直接失败。复用规则：`{SOH,STX,EOT,ACK,NAK,CAN}` 恒为协议；`\r`/`\n` 结束文本行；`'C'` 只有在**当前无未闭合文本行**时才当邀请 |
| 等 ACK 时全程 `ignore_c=True` | 强制升级模式下残留 `'C'` 会排在 ACK 前面（C2） |
| 结束握手后继续收 8s 设备日志 | 解析 `size=… crc=0x…` 与 `UPDATE OK`，与本地 `len`/`crc32` 对拍，给出**确定性结论**（`host_updater` 发完即返回 True，不校验） |
| 默认**不弹**模态确认框 | 模态框默认按钮为 Cancel，被 Esc/回车/关闭取消后流程静默返回，表现为"点了没反应"。现在参数**始终打印到日志区**，勾选框可选开启弹框 |
| 串口收发数据默认打印 | 升级出问题时可从日志直接判断卡在哪一步 |
| 每 Tab 独立的连接对象 | COMTool 已有能力，插件无需特殊处理；串口选择面板由 `PluginItem` 自动注入 |

### 日志前缀约定

| 前缀 | 含义 |
|------|------|
| （空） | 流程日志（插件自己的说明、进度、结论） |
| `!!` / ` *` / ` +` | 错误 / 警告 / 成功 |
| `[MON]` | **串口监视**：未升级时收到的原始数据（按行显示） |
| `[TX]` | 发往设备的整帧（**帧级**，低速模式分块发送也只记一次） |
| `[RX]` | 从设备收到的每个协议字节（受「显示串口收发数据」控制） |
| `[DEV]` | 设备打印的文本日志（始终显示） |

### 串口监视模式

**打开串口后，插件就持续把收到的数据按行打印到日志区**，不需要先点「开始升级」。
这样可以先确认设备活着、是否已进入升级模式：

```
[20:54:53]   已连接。
[20:54:53]   已开启串口监视，收到的数据会显示在下方。
[20:54:53] [MON] BootLoader V1.1
[20:54:53] [MON] ==== BootLoader: UPGRADE MODE (Ymodem) ====
[20:54:54] [MON] CCCCC
```

实现要点：

- `onReceived()` 在**串口接收线程**里把数据通过信号转给 UI 线程，不直接碰控件
- 按 `\n` 切行后渲染：UTF-8 解码、丢弃 `\r`、保留 `\t`，其余不可打印控制字符显示成
  `<06>` 形式（便于判断确实有字节到达）
- 设备只发 `C` 这类没有换行的短数据时，**200ms 空闲自动刷出**已收到的部分，
  避免看起来像"没收到"
- 一旦点击「开始升级」，监视立即停止并清空缓冲，之后的收发由 Ymodem 协议层
  以 `[TX]` / `[RX]` / `[DEV]` 显示；升级结束或断开连接后自动恢复监视
- 日志区最多保留 5000 行（`setMaximumBlockCount`），长时间监视不会占满内存


## 四、使用步骤

1. 左侧选择串口，波特率 **115200**，数据位 8 / 无校验 / 1 停止位，点击 **OPEN**
   - 打开后日志区立即进入**串口监视**，设备打印的内容会实时显示（`[MON]` 行）
   - 此时按一下复位键，应能看到 `BootLoader V1.1` 与 `==== BootLoader: ... ====`
     以及随后的 `CCCC`（`'C'` 邀请），说明设备已进入升级模式
2. 选择**裸 APP bin**（不含固件头），填写 APP 版本 / fw_type / hw_id
   - 「已解析」行会实时回显归一化结果，格式非法会标红
3. 点击 **开始升级**
   - 日志区立即打印本次全部参数，监视模式自动切换到升级流程
   - 状态变为「等待设备邀请('C') ...」
4. **按一下下位机复位键**（若步骤 1 已复位并看到邀请，可跳过）
   - 运行区无有效 APP → BootLoader 持续发 `'C'`，随时可升级
   - 运行区有有效 APP → 复位后 3 秒窗口内发 `'C'`，超时跳转 APP
5. 传输完成后设备回报 size / CRC32，插件自动对拍并给出结论

> **为什么必须手动复位**：若设备运行区已有有效 APP，上电后只有 3000ms 的邀请窗口，
> 用户从"点开始升级"到串口就绪往往超过 3 秒。插件因此进入「持续等待邀请」状态，
> 由用户复位来对齐时序，而不是设一个短超时。


## 五、关键实现细节与已修复的坑

以下是开发过程中实际踩到并修复的问题，后续维护时值得注意。

### 5.1 十六进制解析：`int(x, 16)` 不接受 `0x` 前缀

Python 中只有在 `base=0` 时才允许 `0x` 前缀。写成 `int("0x0101", 16)` 会抛 `ValueError`，
导致所有 `0x` 输入解析失败并回退到默认值。

修复：先剥掉前缀再按 16 进制解析。现在支持 `0x0101` / `0101`（前导零按十六进制）/ `101`（十进制）/ `abc`（0xABC）

> **测试教训**：最初的用例是 `parse("0x0100", default=0x0100)` —— 解析失败后回退到默认值，
> 结果恰好等于期望值，**测试假通过**。现在的用例刻意让输入值与默认值不同。

### 5.2 参数采集漏传 `allowHex` 导致静默回退

`onStartClicked` 里采集参数的 `_parseInt` 调用一度漏了 `allowHex=True`，
即使解析器修好了，点击开始时仍会把 `0x0101` 判为非法并**静默回退成 0x0100**（版本号悄悄写错）。

修复：所有十六进制字段的调用点统一传 `allowHex=True`，并加了 AST 检查作为回归防线。

### 5.3 静默返回路径 → "点了没反应"

`onStartClicked` 的多个提前返回分支原本只弹模态框、不写日志。默认按钮为 Cancel 的确认框被
Esc/回车/关闭取消后，流程静默 `return`，用户看到的就是"点了完全没反应"。

修复：

- **每条分支都写日志**（全文 33 处），无论成败点一下必然有输出
- 确认框改为**可选且默认关闭**，参数**始终打印到日志**
- 弹框挂在顶层窗口上并 `raise_()/activateWindow()`，弹框前后各写一条日志

### 5.4 点击开始后版本框被改写成十进制

`_parseInt` 会回填归一化结果（`setText("257")`），而 `onStartClicked` 直接调用它，
不经过 `onHeaderChanged` 的十六进制回填，于是版本框显示成 `257`。

修复：参数校验通过后调用一次 `onHeaderChanged(silent=True)` 归一化。

### 5.5 离线自测的模拟器需要加锁

`bootloader_ymodem.py` 内置的 `_MockPort` 用于无硬件回归。它的 `read()` 是
「切片 → 删除前 n 字节」，而主机 `write()` 会并发追加设备响应；两者交错时会**误删刚到达的 ACK**，
造成间歇性假失败。真实串口驱动是串行化的，因此给模拟器内部状态加了 `RLock`。

### 5.6 babel 模糊匹配会给新词条注入错译

运行 `comtool-i18n prepare` 时，babel 的 `update` 会用模糊匹配从旧词条猜译文并打上 `fuzzy` 标记，
例如把 `Serial write failed: %s` 猜成 `发送文件失败！`、`ETA` 猜成 `设置`。

处理方式：补齐 zh_CN 后，逐条核对插件词条，**覆盖错译并清除 `fuzzy` 标记**；
zh_TW / ja 中由模糊匹配注入的错译一律清空（回退英文），交由译者补充。


## 六、故障排查

先看日志区，每一类情况都有明确前缀与文案：

| 日志 | 含义与处理 |
|------|-----------|
| `未连接串口，请先在左侧打开串口。` | 先点 OPEN |
| `固件文件不存在：…` | 重新选择文件 |
| `固件过大：N B，设备最多接受 102400 B。` | 裸 bin 超 100KB |
| `文件已含固件头` 警告 | 选到了已经加头的包，应选 `objcopy -O binary` 出来的裸 bin |
| `等待设备邀请 ('C') ...` 后无进展 | 按复位键；或设备根本没进升级模式 |
| `未收到设备邀请，设备未处于升级模式。` | 复位重试；确认串口是 UART2（PA2/PA3）、115200 |
| `文件名包未被确认（等待 ACK 超时）` | 设备擦除备份区耗时数秒；持续超时请确认下位机已烧最新 bootloader |
| `文件名包被设备拒绝 (NAK)` | 固件格式或大小不符（`file_size` 必须是 32+裸bin） |
| `设备中止了传输（双 CAN）` | **最可能：固件头被拒**——`fw_type`/`hw_id` 与下位机不一致，或版本低于设备当前 APP（防降级） |
| `串口写入失败：…` | 串口断开或未打开 |
| `设备已收完数据，但写入/校验失败：…` | 设备侧 Flash 问题 |
| `CRC32 不一致：设备=0x… 本地=0x…` | 传输出错（理论上 CRC16 每包校验能拦住，出现即说明链路异常） |
| `长度不一致：设备=N 本地=M` | 同上 |
| `传输已结束，结果未知` | 结束握手成功但没收到设备的最终日志，可在 8s 后自行按复位观察 |

若「开始升级」后日志只有"已点击…"，说明卡在参数或文件校验，按日志提示处理即可。

### 低速兼容模式

设备端注释已明确整包连发稳定（C3），正常无需开启。若实板上出现反复 NAK / 进度卡住，
可勾选「低速兼容模式」（默认 256B 分块 + 10ms 间隔）再试。

## 八、离线自测

协议核心内置了设备模拟器，**无需任何硬件**即可回归：

```bash
python COMTool/plugins/bootloader_ymodem.py
```

覆盖 13 组场景：CRC 参考向量、包格式、多尺寸端到端（1024/3000/5000/102400）、
文本与协议解复用、NAK 重传、固件头鉴权失败（双 CAN）、防降级、自定义 fw_type/hw_id、
主机侧取消、非法包长度、无邀请超时、ACK 丢失（已知协议局限）、设备 UPDATE 失败。

已知协议局限：**若设备的 ACK 丢失**，主机会重传同一序号，而设备期望的是下一序号 → 持续 NAK →
`pkt_fail`。这是标准 Ymodem 的固有问题，需要设备侧配合重试逻辑才能根治。

## 十、后续可扩展项

- **APP 主动请求升级**：目前依赖手动按复位键。若要让 APP 在收到上位机命令后自行
  「写 `reqUpgrade=0x55` 标志 + 软复位」，需要先在 APP 侧定义命令格式，上位机再加"发送升级请求"按钮
- **DTR/RTS 自动复位**：给 `Serial.ctrl()` 增加 `dtr`/`rts` 支持后，插件可自动拉脉冲复位，
  免去手动按键（需硬件把 DTR/RTS 接到 RESET）
- **波特率校验**：插件目前读不到连接配置，只能提示"需 115200-8N1"；
  如需强校验，可给 `Plugin_Base` 注入只读的连接配置访问器
- **Intel HEX 输入**：当前只接受裸 bin，可加 `.hex` 自动解析并转 bin
